# 短い指示の動作品質と初動の検証

最新の設計指示分離、表情の可逆短縮、移動軸制御と実測は[Astraの品質・速度調査](astra-quality-speed.md)を参照。

現行のJev・部位分離は[Jev調査と反映](jev-research-motion-design.md)を参照。以下は変更ごとの時点記録であり、後着のJev解析を身体条件へ追加した旧経路を含む。

## 2026-09-21: Codexの設計を最初の区間から適用

先に原文だけで身体を生成していた経路を変更した。Codexを選択した場合、最初の身体・表情区間が確定するまでARDYを開始しない。
`realtime_stream` は全体の尺と継続意図を先に宣言し、各区間の動作・尺・継続意図・表情を順に出力する。
最初の区間を再生しながら後続を設計し、`/append` で同じrevisionの末尾へ追加する。通知済みの区間、時刻、表情は変更できない。
未確定の続きを推測して生成せず、既知区間が尽きたときは待つ。計画の失敗・最終検証不一致は明示し、原文生成へ自動で切り替えたり未完成の履歴を保存したりしない。
ARDY単独の明示選択は従来どおりCodexを使用しない。Jevは並行して解析し、利用できる補助情報を後続の身体生成へ反映する。

新規生成は独立したsession。生成中の方向変更と明示的な編集だけ現在の姿勢・履歴を継承する。
方向変更は安全な未来の境界を新しい指示の開始点とし、まだ実行していない計画冒頭を飛ばさない。
`knownUntil` で受信済みフレームの終端をサーバーへ伝え、直前の応答を取消した場合も未受信部分を飛び越えない。
動作切替では過去の条件を引きずらないよう履歴を短くし、同じ動作内では必要な履歴を残す。
停止は計画・推論だけでなくsession作成待ちも解除する。遅れて返った旧sessionは新しい表示を変更せず閉じる。

最初の実Astra評価は3件で最初のVRMAまで8.04〜9.01秒、最初のdeltaまで5.11〜5.63秒だった。
複合入力2件は全計画完成の3.16〜4.11秒前に再生開始できたが、途中に389〜804msのバッファ不足もあった。
これはNodeのVRMA構築までの測定で、ブラウザ描画時間や実Jev通信を含まない。即時生成を達成した数値ではない。

同じ標本の映像確認では「拾う→差し出す」は順に実行された一方、歩行で腕が上がり、別の複合動作の最後のしゃがみが浅すぎる問題が残った。
通信・時刻・保存の合格と、動作の正しさは別に記録している。記録: `release/ardy-authored-session-eval/results.json`、`visual-assessment.md`。
説明文が以前の短い現在形のcaptionから、命令形の冗長な文へ変わっていたため、元の一般的なcaption形式へ戻した。
公式ARDYの `scripts/interactive_demo/common.py` の入力形式も参考にした。動作名ごとの特例・固定モーション・本番固定seedは追加していない。

caption形式へ戻した後も、実Astra→ARDYを同じ3入力で毎回新規生成して映像と関節軌跡を確認した。

| 入力 | 最初のVRMA | 再生中のバッファ不足 | 映像・軌跡での確認 |
| --- | ---: | ---: | --- |
| その場で歩く | 9.81秒 | 0秒 | 脚は交互に動くが腕を頭上まで振り、普通の歩行として不適切 |
| 左手を一度振ってから、右を向き、ゆっくりしゃがむ | 7.86秒 | 2.24秒 | 左手と方向変更は出る。最後の腰下降は約0.038mで、しゃがみ未達 |
| 足元の小さな落とし物に気づき、慎重に拾って相手に差し出す | 9.50秒 | 0秒 | 見下ろす→屈んで手を伸ばす→差し出す大枠は出る。指先の把持は未評価 |

caption文体だけで品質が改善したとは判断できない。計画の指示と生成された骨格が一致しない標本を、成功例として数えない。
最初のdeltaまで5.42〜6.70秒で、初動遅延の主因は引き続きCodex側にある。各入力1標本であり、成功率の評価ではない。
最新記録: `release/ardy-authored-caption-eval/results.json`、`visual-assessment.md`、前面・側面画像とVRMA。

別途、旧逐次生成の `lowLatency=true` と新sessionのモデル入力を3計画で比較し、履歴長・推論窓・prefixの一致を確認した。
これは旧通常生成との同等性を意味しない。通常生成の複合動作には、各動作を独立生成して位置・向きを合わせてつなぐ経路がある。
現在の逐次方式は姿勢履歴を継承するため、その条件が新しい動作を妨げる可能性は残る。
空のfuture枠は公式モデルでattention対象にならないため、枠だけ増やす変更は行わなかった。
Codexの設計を確実に使う修正と、ARDYの任意動作への忠実度・初動速度の改善は別の達成条件とする。

## 2026-09-21: ループ回帰と表情待ちの修正

逐次生成で `spec.loop=false` と単発再生を固定しており、「つながるループ」の選択が無視されていた。
完成した全長クリップだけに「自動／つながるループ／1回」を反映し、生成途中の短い区間は反復しないように修正。
自動はCodexの `continuous` を優先し、有限回数・終了姿勢のある指示は単発とする。
完成時の切替では再生位置を接続ループの位相へ写し、短い補間でつなぐ。
書き出しは身体・位置・表情の接続を焼き込み、アプリへの再読み込みで二重に接続加工しない。

最初の身体チャンク内にあった表情計画の完了待ちも除去した。顔が未完成でも生成済みの身体は再生する。
顔の完成を捏造せず、生成失敗や取消では未完成クリップを履歴や書き出し対象にしない。

## 確認された問題

- 短い指示を単に英語の動作名へ変換するだけでも、長い姿勢説明へ膨らませても、ARDYが求めた動作を十分に出さないことがあった。
- 長さが「自動」でもリアルタイム経路は6秒へ固定していた。単発のジャンプやお辞儀にも、追加の動作を生成する余地ができていた。
- 40フレームの履歴は滑らかさを支える一方、手振りなどで動きが止まる状態を引き継ぐことがあった。
- Jevの開始時の感情が遅れて届くと、Codexが設計した後半の表情を上書きした。
- 停止してもCodex側の推論が残り、新しい指示が「生成中」で弾かれる経路があった。

## 共通処理の変更

動作名別の置換分岐・準備済みクリップは追加していない。Codexが任意の指示から、中心となる動作、必要な身体部位・周期・接触・移動条件を簡潔な記述にする。`continuous` は指示全体の意味から判断し、継続動作は履歴4、有限の動作は履歴40とする。自動尺もCodexの計画に従い、明示した秒数は維持する。

身体計画の完全な配列を受信した段階でARDY推論を開始し、表情の出力と重ねる。表情は同じ6値を短い配列で転送する。
最初の身体チャンクは表情の完了を待たずに再生する。未生成の顔は別の演技で埋めず、計画が届いた後の更新で現在の再生時刻へ反映する。
完成・履歴保存・書き出しは、身体と表情の両方が検証できた後。取消は実際のCodexターンまで伝える。

Jevの先行反応は強さを抑え、身体の再生が始まった後に届いた開始時の感情は上書きに使用しない。低信頼度のゼロ値で設計済みの表情を消さず、使わなくなった表情・視線は滑らかに戻す。

## 検証と限界

履歴長の比較は同じ計画・同じシードで32回実行した。手振りでは3シードとも履歴40で終盤の活動が最初の10%未満になり、履歴4では3シードとも継続した。短い履歴は境界の揺れが増えるため、全動作へ一律には適用していない。

変更後の5種類の短い日本語入力は、実Astra・実ARDY・VRMA生成まで通った。初回再生は5.2〜12.6秒で、まだ即応とは言えない。歩行開始が鈍い例も残り、全ての短文で自然さや回数・接触の忠実さを保証できる段階ではない。数値の活動量やテスト合格を、演技品質の合格とは扱わない。

保存した最終5例をアバター表示と全フレームの関節位置で確認した結果は以下のとおり。これは各1回の標本であり、成功率の推定ではない。

| 入力 | 最終標本で確認した動作 |
| --- | --- |
| その場で歩く | 最初の約2秒はほぼ静止、2〜4秒に足踏み、終盤は再びほぼ静止。継続歩行としては未解決。 |
| 手を振る | 終了時も腕を上げているが、途中で下げて再開する。 |
| 拍手する | 動作は継続する。手のひらの接触・向きの正確さは未確認。 |
| ジャンプする | 最後は着地するが、2回跳ぶ。単発動作の回数は未解決。 |

終盤2秒の可動域にはその窓の前半の動きも含まれ、最後の停止を見落とすため、検証スクリプトには最後1秒の可動域も記録する。可動域だけで指示への忠実さは判定しない。画像と全フレームの関節記録は `release/realtime-final-prompts/contact-sheet.png` と `contact-joints.json`。

Jevの実キーによる精度・速度は今回の実測に含めていない。

## 参考製品との設計上の違い

ユーザー提供のAnimeAct Engine製品説明では、会話向け上半身モーション40種をキャラクターの骨格に合わせて初回に生成し、演技JSONから表情・視線・頭・身体・間を制御する。腰から下は動かさない。実行時に固定JSONやゲーム内ルールで動かせることは、任意の全身動作を毎回推論して即座に生成できることを意味しない。内部コードや実測速度は確認していない。

Text-To-VRMAは、任意の短い指示をCodexが動作計画へ変換し、ARDYが毎回全身モーションを新規生成する方針。参考にするのは、演技を独立した表情・視線・身体トラックで扱い、同じ時間軸で同期・部分修正できる設計である。固定モーション集への変更や上半身限定化は行っていない。

今後の全身リアルタイム化には、初回計画待ちの短縮に加え、再生中の姿勢・速度を引き継いだ未来区間の再計画と、動作開始・継続・回数・接触の検証が必要。表情だけを先に動かすことと、指示された全身動作が即応することは別の達成条件として測定する。

## 具体例の削除と新規入力の独立化

動きが似るという報告を受け、生成用プロンプトに残っていた振り付け例、モーションJSON見本、感情ごとの仕草表を削除した。通常LLM生成にあったランダムな未指定動作の追加と、キーワード一致で腕・手首を固定した手振り形へ上書きする処理も削除した。座標規約・JSON構造・一般的な可動域のガードは保持している。

通常の新規生成は、前回の指示・姿勢・表情をCodexとJevに渡さない。Ctrl / ⌘ + Enterも再生中に新規生成する。前の演技への追加修正はCtrl / ⌘ + Shift + Enterに分離した。Jevの定型的な身体反応分類 `reaction` とその確率はリアルタイム身体計画に注入しない。感情・強度等の補助情報は残す。

自動テスト166件・ビルドと、ブラウザでの新規送信・表情修正・停止・進捗表示を確認した。保存済みモーションのキャッシュ再利用、固定シード、前回のCodexスレッド再利用は見つかっていない。

例削除後の新しい複合入力2件も実Astra→ARDYへ通したが、回転要素を落とす標本があった。保存した同じ計画をseed17でhistory4/40の各1回だけ比較しても、一回転にはならず、履歴4のほうが回転が少なかった。例や過去の状態への誘導を除くことと、ARDYが任意の複合動作へ正確に追従することは別である。記録は `release/realtime-free-inputs/results.json` と `history-diagnostic.json`。推論ステップ数・CFGの寄与は今回比較しておらず断定しない。
