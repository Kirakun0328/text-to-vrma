# モーション品質の調査（2026-09-05）

結論: 現状が限界ではない。Astraによる指示理解の改善と、身体運動・接地・リターゲットの改善は分けて評価する。以下の優先順位はコードと一次資料からの推定であり、生成結果の比較実験は未実施。

## 主題: GPT-6自体の能力をもっと使うには

単なるモデル差し替えより、GPTに渡す情報と修正手段を変える方が有望というのが今回の実装調査からの仮説。現在は「文章→関節角度のJSON→同じJSONを読んで自己修正」であり、GPTは実際に再生した姿勢を見ていない。

推奨する次の試作は、Astraによる演技設計→キーポーズ生成→描画と数値評価→Astraによる修正、という反復経路。

1. 演技設計を分離する。動作の段階、タイミング、支持脚、重心移動、視線、手の到達点、終了姿勢を先に明示させる。
2. 骨格の実寸と姿勢評価を渡す。関節角度を推測させるだけでなく、順運動学で得た手足の位置や床との距離を返す。到達点から関節を解くIKを組み合わせる案も比較する。
3. 主要時刻の姿勢を正面・側面から画像化し、元の指示と一緒にAstraへ戻す。画像入力対応は公式確認済みだが、三次元の接触や奥行きは画像だけでは曖昧なので数値評価を併用する。
4. 修正は問題のある区間・関節に絞る。上限回数を設け、評価が改善した結果を採用する。高い推論設定も比較対象にする。

まずはLLMモードの「手を振る」「お辞儀」「片足でバランス」「しゃがんで立つ」を、Solの現行方式・Astraの現行方式・Astraの反復方式で比較する。特に意図への忠実さ、ポーズの説得力、タイミングに改善を期待できるが、足滑りや物理的整合性の改善をモデル名だけで保証はできない。

これは新しいモーションモデルの導入ではなく、GPTを演技の設計・検証・修正に使う方式。後続の実装で、計画→生成→正面・側面の画像レビュー→再計測を追加した。修正は1回、悪化した候補は比較用に残し初稿を採用する。到達位置は生成指示と評価に使用し、IKによる強制配置は未実装。

CodexのChatGPTログインでも同じ処理を利用可能。ローカルWeb版はViteの同一オリジンの中継から既存のCodex App Serverクライアントを利用する。CLI 0.144.1ではAstraが一覧に出なかったが、同じアカウントで0.153.3を使うと `gpt-6-astra` が一覧に現れた。プロジェクトに0.153.3を固定して追加し、プロジェクト内のCLIを優先する。

実動確認: GPT-5.6 SolをChatGPTログインで使用し、3秒のお辞儀について計画→生成→実VRM画像で修正→再計測を完走。計画上の支持脚の滑りは16.22→0.04 cm/s、足首の静止高からの沈み込みは0.79→0.32 cm、目標位置の平均誤差は14.62→9.67 cmだった。1例の近似指標であり一般的な品質向上の保証ではない。

## GPT-6 Astra対応

- APIモデルIDは `gpt-6-astra`。公式資料でChat Completions、ストリーミング、Structured Outputsの対応を確認。既存のOpenAI送信経路を使用する。
- UIの4言語に選択肢を追加。選択時に保存し、ARDYの計画にも反映する。既定の `gpt-5.6-sol` は維持。
- 公式資料では段階提供中。利用するAPIプロジェクトの権限は別途必要であり、この作業では実APIの利用可否や品質差を確認していない。
- 標準料金は100万トークンあたり入力$10、出力$50（通常の短いコンテキスト）。自己修正を有効にすると追加の呼び出しが発生する。

出典: [OpenAI GPT-6 Astraモデル情報](https://developers.openai.com/api/docs/models/gpt-6-astra)、[モデルガイド](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra)

## 現在の実装と改善の優先順位

| 優先度 | コードで確認した状態 | 改善案と期待する効果 |
|---|---|---|
| 1 | `src/specMerge.js` の `appendNeutralEnding` は0.8秒で直立へ戻す。`isLoopFriendly` は腰の水平移動量で判定する | 座る・倒れる・寝る動作は終了姿勢を保持。ループは全身姿勢と速度の連続性も評価し、巻き戻りや瞬間的な起き上がりを抑える |
| 1 | ARDYの `post_process_motion` は既に足接触を使う。一方 `retarget.py` は回転の転写と固定の腰高比による変換で、足接触情報は最終specに残らない | 接触情報を保持し、対象VRMの脚長・足位置に合わせて接地IKを適用。生成元では接地していても体型変更後に滑る問題を検証する。書き出しにも補正を反映する |
| 2 | 複合動作は経由地なしの場合に独立生成し、6フレームでクロスフェード。動作切替を確実にする意図がコードに記載されている | 前後の速度、支持脚、重心を考慮して接続区間を作る。履歴の引き継ぎだけに戻すと次の動作が出なくなる既知の問題があるため、接続区間の制約付き生成を比較する |
| 2 | LLMは1秒2〜4キー程度のオイラー角を生成し、VRMAではLINEAR/球面補間。自己修正は同じJSONを読む方式 | 関節可動域だけでなく足滑り、床貫通、速度変化を数値評価する。描画した複数方向の画像を使った再評価も候補。キーを増やすだけでは運動の整合性は保証されない |
| 2 | LLMには手首・肩を動かさない指示があり、指は固定カール。上腕などは強くクランプされる | 動作ごとの手形と、体型に応じた可動域・衝突回避を導入。Astraが良い演技を設計しても固定ルールで失われる箇所を検証する |
| 3 | ARDY連携の空間制約は `Root2DConstraintSet` による経路が中心 | 手の到達点や全身キーポーズも条件として与え、拍手・手を伸ばす・着座などの位置精度を上げる |

ARDY公式は経路・全身キーフレーム・疎な関節位置／回転の制約をサポートしている。現在の連携を拡張する余地がある。ただし使用中のCoreモデルとの適合性は実装時に検証する。

出典: [ARDY公式実装](https://github.com/nv-tlabs/ardy)。接触を使った足滑り改善の研究例: [StableMoFusion](https://arxiv.org/abs/2405.05691)。論文の結果がこのVRM変換経路にもそのまま当てはまるとは限らない。

## 別モデルへの変更はどうか

HY-Motion 1.0は比較候補。公式には1B版と0.46BのLite版があり、最低VRAM目安はそれぞれ26GBと24GB。追加のプロンプト処理用LLMはこの数値に含まれない。導入負担が大きく、ARDYよりこのアプリで良くなるという比較結果は得ていないため、先に既存経路の品質損失を直す方針を推奨する。

出典: [Tencent HY-Motion公式実装・要件](https://github.com/Tencent-Hunyuan/HY-Motion-1.0)

## 品質を確認する比較方法

同じVRM・同じ秒数で「手を振る」「歩いて止まる」「ジャンプして着地」「椅子に座って保持」「横になって保持」「歩く→振り返る→手を振る」を比較する。ARDYは同じseedを複数用意し、LLMのランダムな演出も比較時には揃える。

評価項目は、指示の達成、接地中の足の移動量、床貫通、関節の急な速度変化、ループ境界の姿勢差、生成時間、API使用量。実際の出力を比較するまで「Astraだけで大幅改善」「モーションキャプチャ品質を保証」とは判断しない。
