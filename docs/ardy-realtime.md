# Codexが区間ごとに設計するARDY連続生成

更新: Jev解析待ちは廃止した。JevとAstraを並行開始し、区間確定時に許可された項目だけ補助する。以下の解析を先に待つ説明は旧方式。[現在の構成](jev-parallel-integration.md)を参照。

最新の区間切り替えと初動の修正は[複数動作の検証](sequence-transitions.md)を参照。Codexからの部位・移動軸の値は短い整数表現で受け取り、従来の配列に展開してARDYへ渡す。

Codex併用では、最初の動作区間の身体・表情・長さが確定してからARDYの身体生成を始める。
その区間を生成・再生している間に、Codexが後続区間を設計する。確定済み区間の内容や時刻は変更せず、末尾へ追加する。
Jevの意味解析を既存の時間上限内で取得してからCodexへ渡す。キー未設定なら即座に進み、接続失敗・時間切れでも原文から設計する。
明示的に「ARDYのみ」を選んだ場合は、入力文から直接生成を始め、Codexを呼ばない。
動かす身体部位は毎回新しく推論する。表情・視線・頭部だけの区間は保持姿勢と生成した数値トラックで実行し、不要な全身推論を省く。固定の振り付け、動作ライブラリ、生成済みクリップの再利用はない。

区間の`rootAxes: [x,y,z]`は平行移動を許す方向を表す。水平移動禁止でも上下動・骨盤回転・脚運動は別に扱う。制限後の姿勢を次の生成履歴へ反映する。表情の`[]`は中立、各行の末尾のゼロは省略でき、受信側で元のウェイトへ戻す。旧形式も受け付ける。最新の検証と制約は[Astraの品質・速度調査](astra-quality-speed.md)を参照。

## 操作

1. ARDYサーバーを最新版で起動する。古いプロセスは再起動が必要。
2. 通常の入力欄から生成する。Codex選択時は「最初の動作区間を設計中」と表示し、その区間が揃うと生成・再生を始める。
3. 生成中のCtrl / ⌘ + Enterで新しい指示を送ると、同じセッションの物理的な履歴から未来の動きを変更する。
   前の動作の意味やJev解析を新しい指示に持ち越さない。明示的な追加修正はCtrl / ⌘ + Shift + Enter。
4. 生成ボタンを再度押すと停止する。停止や別の履歴クリップの再生でセッションも閉じる。
5. 完成後は履歴に1件登録し、VRMAを保存できる。「つながるループ」「1回」「自動」は完成クリップに適用する。
   生成途中のチャンクは繰り返さない。

APIキーは設定欄で従来どおり自動保存する。Jevのキーがあれば自動で解析する。
Jev未設定・接続失敗・低い総合信頼度で身体生成を止めない。項目ごとの確信度を補助の強さに使う。
Codex選択時の未認証・計画失敗はエラーとして表示する。直接生成へ自動で切り替えず、不完全な結果を完成履歴に登録しない。
ARDYの直接生成を使う場合は、利用者が「ARDYのみ」を選ぶ。

1つの指示は2〜30秒、既定6秒・8推論ステップ。Codexは全体の尺を最初に宣言し、手動尺では指定値、自動尺では動作に必要な長さを使う。
1〜12区間で構成し、各区間は0.4秒以上・0.2秒単位。確定後に時間を比例調整しない。
同じ動作を続ける指示を時間だけの都合で分割せず、意味のある動作の変化で区間を分ける。
ARDY単独で3候補・経由地・30秒を超える手動尺を選んだ場合は、それらを扱える既存の一括生成へ切り替える。
OpenAI API／Claude APIを選んだ場合も既存の生成経路を使う。

## 実装

`src/ardyLiveSession.js` が `tools/ardy-engine/rolling_sessions.py` の次のAPIを使う。

| API | 動作 |
| --- | --- |
| `POST /sessions` | 状態を確保して即応。翻訳・テキストエンコード・GPU推論はここで待たない |
| `POST /sessions/{id}/next` | 最新の指示と保持中の物理履歴からモデル固有の1 horizonを生成 |
| `POST /sessions/{id}/append` | 同じrevisionのまま確定済み計画の末尾へ区間を追加。既存区間・開始時刻・生成済みフレームは変更しない |
| `POST /sessions/{id}/update` | 再生済みの区間と短い先行バッファを保ち、その先の条件を変更 |
| `POST /sessions/{id}/close` | 保持履歴を解放し、古い推論結果の確定を防ぐ |

接続元は `app://bundle` とHTTP(S)の `localhost`・`127.0.0.1`・`[::1]` を検証する。
`localhost` の開発画面から `127.0.0.1` のARDYへ接続すると、ブラウザは `Sec-Fetch-Site: cross-site` を送る。
正規のOriginを確認できる場合はこのヘッダーだけで拒否しない。外部Origin・不正なHost・不明な接続元からのcross-site要求は引き続き拒否する。

新しい指示への更新と推論にrevisionを付ける。計画待ちやGPU計算が古い指示のまま完了しても採用しない。
同じ計画の末尾への追加はrevisionを変えないため、実行中の正しい推論結果を破棄しない。
まだ設計されていない区間には進まず、`next`の`waiting`応答で次の区間を待つ。全区間が検証されると`planComplete`を確定する。
更新はGPUロックを待たない。実行中のGPUカーネル自体の即時停止はしない。
推論を無制限に先行させず、実際の再生位置を見てバッファを補充する。一時停止はチャンク受信後も維持する。
Pythonは有限の過去履歴だけを保持し、ブラウザが書き出し用の全トラックを蓄積する。

`src/realtimePlan.js`の`planRealtimeMotionStream`は、全体の継続指定・尺と、身体・表情を含む区間を順に受け取る。
区間の完全なJSONと時間・表情を検証してから`onSegment`を通知する。後続区間や応答全体の完成を待つ必要はない。
全体の完成時には、通知済みの区間が変更されていないことと、区間の尺の合計を再確認する。
身体も表情も最初からCodexの設計で再生し、区間の順序・時刻・再生済みのキーを保つ。
区間の切替直後は物理履歴を短くし、直前の動作が新しい指示を妨げるのを抑える。継続動作の区間では短い履歴を使う。
CodexはJevの部位・視線・感情・時間変化の確率を原文とともに解釈する。Codex設計済みの本文へJevの感情語を後付けしない。ARDY単独では従来のスタイル補助を未来区間へ渡す。
Jevの独立した感情スコアは、再生開始前の先行表情や、ARDY単独で未設計の顔の開始表情に使用する。
Codexの区間表情、既に過ぎた開始表情、新しい明示的な顔修正を後着の解析で上書きしない。

各区間の`body`はroot・torso・head・左右腕・左右脚の7部位から必要なものを指定する。固定仕草の分類ではない。
`root`は骨盤の向きと位置、腕は肩から指、`head`は首と頭を所有する。必要な支持動作もCodexが含める。
指定外の局所関節角は区間開始時の実際の姿勢を保持し、補正結果をARDYのネイティブ履歴へ戻す。
新規開始の基準は骨格形状から作る腕を下げた立位であり、動作クリップを使わない。
`body: []`は全身推論・文章エンコードを省略する。全部位の指定は従来どおり制約なしで生成する。
`head`・`gaze`の数値カーブは独立に実行し、視線を標準VRMAのlookAtトラックにも保存する。
詳しい根拠と実装の対応は[Jev調査](jev-research-motion-design.md)を参照。

| 入力の扱い | 履歴と文脈 |
| --- | --- |
| 通常の新規生成 | 新しいセッションを使う。前回の身体履歴や指示を条件にしない |
| 生成中の再入力（`replaceActive`） | 同じセッションの現在姿勢から未来を変更。前の動作の意味は引き継がず、姿勢・再生位置・表情を計画へ渡す |
| 明示的な追加修正（`continuation`） | 現在の動作の文脈も計画へ渡し、保持中の物理履歴から続きを生成する |

完了したセッションも最初の再生中は保持し、明示的な追加修正につなげられる。通常の新規生成では使用しない。サーバーの非活動時TTLは180秒。
期限切れ・サーバー再起動時は自動で新規セッションを作る。
完成ループの2周目以降・末尾の接続ブレンド区間・過去へのシークは、保持中のARDY時間軸と一致しないため新規生成に戻る。
画面上の任意の現在ポーズをARDYの生成履歴へ逆変換する処理は未実装。

## 進捗・制約

最初の設計待ちでは段階を表示し、身体生成開始後の進捗は予定尺に対する受信済みフレーム量で表示する。
計画・身体生成が完了し、完成データの再生準備ができた後だけ100%にする。
初動・revision・Jevの使用箇所は `spec.realtime` に記録する。
同欄の`authoredFromStart`・`plannedSegments`・`plannedDuration`で、Codex設計の利用と受信済み区間を確認できる。
後続の設計や生成が再生に追いつかなければ、最後に受信した姿勢で待つ。未設計の動作を代わりに生成しない。

これは生成中に再生し、途中入力で続きを変える実装であり、毎指示の上限をなくした無期限の自動生成ではない。
Codex併用の初動は、Jev通信（設定時）・最初の区間設計・身体が必要な場合のCPUテキストエンコードとGPU推論・VRMA変換と読み込みに左右される。
ARDY単独の日本語入力では翻訳時間も加わる。この区間設計方式の速度・指示追従は、旧方式の計測と分けて評価する。
1秒以内の初動や、任意の短文への正確な動作を保証しない。未受信のフレームは最後の姿勢で待つ。
音声との同期は未実装。Jevの実API精度・通信時間は今回の自動計測には含まない。

Horizon8は20fpsで0.4秒の未来を出力する別モデルで、0.4秒以内の応答を保証するものではない。
このPCの12ケース比較では初動短縮が平均約93msで、H8に歩行欠落・手振り減衰が見られたためHorizon40を維持する。
比較結果は `release/ardy-horizon-comparison/results.json` と同フォルダのREADMEに保存した。

根拠: [ARDY公式実装](https://github.com/nv-tlabs/ardy)、[研究ページ](https://research.nvidia.com/labs/sil/projects/ardy/)。
過去の計測との違いは [品質と遅延の記録](realtime-quality-latency.md) を参照。

## 変更前の方式で確認した記録

以下は、身体の直接生成をCodexより先行させていた方式での検証記録。今回の区間設計方式の性能測定ではない。

- JavaScript 205件、Python 29件と本番ビルドが通過。既存のバンドルサイズ警告は残る。
- ブラウザのサービスモックで、ARDY単独時のCodex呼出ゼロ、同セッション更新、Jevの身体・顔補助、
  手動一時停止、ループON/OFF、履歴、VRMA保存・再読込、停止・失敗時の履歴除外を確認。
- 実ARDY単独2件と同セッション指示変更1件、実Astra併用1件で生成・VRMA構築・再生済みデータの不変性を確認。
  初動は約0.56〜0.98秒（Nodeの構築時間）。Astraの計画更新時に約0.2秒のバッファ不足が残る標本がある。
- 日本語翻訳の反復をbeam探索の確率再正規化で修正。特定のプロンプトへの置換ルールは追加していない。
- モックなしの実ブラウザでも「その場で歩く」を確認。ARDY単独・Jevキーなし・8ステップで最初の実描画844ms、
  6秒分の生成完了3.49秒。両脚の動作、終端停止、履歴登録を確認した（1標本での測定）。
